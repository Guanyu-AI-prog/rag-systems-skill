# Agent Harness 设计模式

Agent Harness = 给LLM套缰绳——通过Prompt约束、工具定义、路由逻辑、行为控制让LLM在Agent场景下表现稳定。

## 核心架构

```
用户输入 → 分类器 → 路由选择 → 执行 → 降级 → 输出
```

### 三路路由模式 (来自 dx_agent.py)

| 路由 | 触发条件 | 行为 |
|------|----------|------|
| **simple** | 单点查询，无对比/计算 | 直接RAG | 
| **comparison** | 含对比关键词或2+档位数字 | 每实体独立搜索+LLM对比 |
| **complex** | 含计算/推荐/多跳推理 | 完整Agent循环，可调用工具 |

## Harness的5个层次

| 层次 | 内容 | 实例 |
|------|------|------|
| **Prompt约束** | 身份、输出格式、行为边界 | 求职教练5模块框架 |
| **工具定义** | 哪些工具可用、参数要求 | dx_agent的3个工具 |
| **路由逻辑** | 如何分类和分配 | classify_query三路路由 |
| **降级策略** | 失败时怎么办 | Agent→fast_path→"请联系客服" |
| **熔断保护** | 连续失败自动停止 | circuit_breaker |

## Agent Harness退化问题

随对话变长，system prompt约束会被稀释：
- **位置问题**：初始规则在长对话中被后续内容掩盖，模型注意力偏向最新消息
- **覆盖问题**：聊久了，原始约束被对话"浸泡"软化
- **模型天然倾向**：LLM更关注"最近说了什么"而非"一开始怎么定的规则"
- **温度无关**：Harness退化是上下文长度问题，不是temperature问题（即使temperature=0.7默认值，长对话一样会飘）

### 解法
| 方案 | 做法 | 代价 |
|------|------|------|
| 定期/reset | 固定轮数后新会话 | 丢对话记忆 |
| 上下文压缩 | 早期内容压缩为摘要 | 细节丢失 |
| 反复注入约束 | 回答末尾重复核心规则 | 占token |
| 工作流拆分 | 一session干一件事 | 交互割裂 |
| **温度控制** | 设temperature=0.1降低模型发散倾向 | 回答多样性略降 |

**关键认知**：退化不是temperature问题——即使temperature=0.1，长对话一样会漂。温度只改变漂移速度，不改变方向。真正修复是让/new成为习惯。

**实用检测信号**：当你发现Agent开始编造不合逻辑的比喻、忘记之前定的输出格式、说话风格突变——Harness已经在退化了。此时 /new 是最快修复。

## Agent Harness实战：非开发者视角

Agent Harness设计不是程序员专利。用户（关彧）的实践路径证明了另一种成长模式：

**不手写代码，但设计架构。** 核心能力：
- 定义行为边界（什么能说什么不能说）
- 设计交互流程（分批3-5张截图再处理）
- 控制工具权限（哪些工具开哪些关）
- 迭代约束规则（从1200字精简到500字）
- 用Agent写Agent（让Hermes帮忙写dx_agent的代码）

**这与传统开发者的区别：**
- 传统路线：学语法→写代码→搭系统
- Harness路线：定义需求→让AI写代码→验收修改→迭代约束
- 前者懂实现，后者懂控制。在企业Agent部署场景中，后者更稀缺

## "能用" vs "有用"：Agent价值的分水岭

| | 能用 | 有用 |
|------|------|------|
| 定义 | 能跑通、能返回结果 | 在生产环境稳定运行三个月 |
| 标准 | API调通、搜索有结果 | 用户不骂、老板不撤、维护成本低于收益 |
| 难度 | 现在任何人都能做（Workbody等工具） | 需要踩过所有坑才知道 |
| 护城河 | 无 | 踩坑经验+业务理解+兜底设计 |

**核心洞察：** "能用"是技术实现，"有用"是工程落地。中间隔着：路由设计错了会崩、Prompt长了会被稀释、降级没做好熔断了就傻眼、法条改了知识库没更新就胡说。这些只有真正跑过生产环境的人才知道。

**面试表达：** 不要说"我会搭Agent"，要说"我知道怎么让Agent在三个月内不出问题"。

## 企业级Harness思路

```
同一Agent引擎
  ├── Harness#1: 客服组（热情/守边界/订单工具）
  ├── Harness#2: 销售组（主动推荐/CRM工具）
  ├── Harness#3: 技术组（严谨/日志工具）
  └── 管理后台（统一日志+知识库更新）
```

每个Harness=不同Prompt+不同工具集+不同知识库范围，底层引擎共享。

## 关键认知

- **Agent Harness ≠ 手写代码**。核心是设计行为边界和响应逻辑，不是实现细节
- **大部分RAG错误不是检索问题，是LLM推理问题**。fix在Prompt不在检索
- **Harness质量由业务理解决定**，不是由技术深度决定
- **所有Harness都会退化**，习惯定期刷新是关键运维手段
